# 构建确定性医疗分诊引擎：为什么规则引擎比 LLM 更适合安全红线

> 这是我们构建 [Family Health Doctor](https://github.com/liliwen88/doctor.skill) 这个 Agent Skill 的技术分享。我会讲清楚为什么在医疗安全的场景下，我们选择了确定性规则引擎而不是 LLM 来做分诊，以及整个架构是如何设计的。

---

## 项目一句话介绍

**Family Health Doctor** 是一个开源的 AI 医疗助手 Agent Skill，兼容 SkillsMP、腾讯 SkillHub、Claude Code 等平台。它提供 10 大功能：分诊评估、症状分析、预防保健、慢性病管理、药物查询、检验解读、儿科护理、文献检索、临床试验搜索和 SOAP 临床记录。

## 核心设计决策：分诊系统为什么不用 LLM

医疗分诊是一个特殊的场景——**漏判一个紧急情况就可能危及生命**。在项目初期，我们面临一个关键选择：

| 方案 | 优点 | 缺点 |
|------|------|------|
| **LLM 直接分诊** | 灵活、能处理非结构化输入 | 不可审计、有幻觉风险、同一个症状可能给出不同的分诊结果 |
| **确定性规则引擎** | 可审计、可测试、结果一致、零延迟 | 覆盖范围受规则数量限制 |

我们选择了**确定性规则引擎**，具体原因有三个：

### 1. 可审计性

规则引擎的每一行决策都是透明的。当系统判定"胸痛+大汗+左臂放射痛 = 紧急"时，你可以直接追溯到具体的规则：

```python
("胸痛", "大汗", "放射", "左肩", "左臂", "下颌"),
"急性冠脉综合征 / Acute Coronary Syndrome",
"立即拨打 120/911，嚼服阿司匹林 300mg（无禁忌），保持静卧",
```

而 LLM 的决策是一个黑盒——你永远不能 100% 确定它为什么做出某个判断。

### 2. 可测试性

规则引擎可以直接用单元测试覆盖每一个危险信号模式。我们的测试套件覆盖了：

- **8 个身体系统**（神经、心血管、呼吸、消化、精神、儿科、产科、普外科）
- **~30 个危险信号模式**，每个至少 2 个关键词才触发
- **4 个分诊级别**（紧急/加急/常规/自我护理）

```python
def test_emergency_stroke_fast():
    """单侧无力 + 言语不清 → 紧急（脑卒中）"""
    result = triage(TriageInput(
        symptoms=["单侧肢体无力", "言语不清", "口角歪斜"],
        onset="sudden", severity="severe"
    ))
    assert result.level == "emergency"
    assert any("脑卒中" in rf for rf in result.redFlags)
```

51 个单元测试，0.15 秒跑完全部。如果用 LLM 做同样的事情，你根本没办法写确定性的测试。

### 3. 结果一致性

同一个症状输入，分诊结果永远相同。这在医疗场景中至关重要——你不会希望同一个病人今天被分到"自我护理"，明天同样的症状变成"紧急"。

## 架构设计：三明治模式

整个技能采用 **API 优先 + AI 回退 + 规则引擎做安全门** 的三明治架构：

```text
用户输入
  │
  ▼
┌─────────────────────┐
│  🔴 分诊安全门        │  确定性规则引擎（非 LLM）
│  紧急检测 → 停止所有  │  ← 这一层必须在 AI 之前
│  后续处理             │
└─────────┬───────────┘
          │ (非紧急)
          ▼
┌─────────────────────┐
│  SKILL.md 路由层     │  10 个功能分发
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│  Python API 脚本     │  OpenFDA / PubMed /
│  (9 个，纯标准库)    │  DailyMed / RxNorm /
│                     │  ClinicalTrials.gov
└─────────┬───────────┘
          │ (API 失败时)
          ▼
┌─────────────────────┐
│  AI 模型回退         │  使用模型知识库兜底
└─────────────────────┘
```

**关键洞察**：安全门必须在 AI 之前。让 LLM 先看到"胸痛+大汗"再判断要不要紧急处理，不如用规则引擎在输入阶段就直接拦截。

## 数据源策略：多级回退保证可用性

药物查询是一个典型的多级回退案例。我们集成了 3 个数据源：

```
查询药物信息
  ├── 1️⃣ OpenFDA Label API（药品说明书）
  │     └── 失败? → 2️⃣ OpenFDA Event API（不良反应报告）
  │           └── 失败? → 3️⃣ DailyMed / RxNorm（NIH 药物数据库）
  │                 └── 全部失败? → AI 模型知识回退
```

每一层失败都自动降级到下一层，用户无感知。所有 API 都是免费公开的，不需要申请 key。

## 为什么 Python 只用标准库

9 个 Python 脚本不依赖任何第三方包。这不是技术洁癖，而是：

1. **零安装成本**——用户不需要 `pip install` 任何东西
2. **CI 简单**——不需要管理依赖版本
3. **平台兼容**——SkillsMP 和 SkillHub 的执行环境不需要预装特定包
4. **安全审计简单**——依赖树为空，审计面积极小

代价是 HTTP 请求要用 `urllib.request` 而不是 `requests`，JSON 解析没有自动重试。但在医疗场景下，可控性 > 便利性。

## 从中学到的经验

1. **不是所有场景都适合 LLM-first**。安全性敏感的决策（医疗分诊、金融风控、自动驾驶决策）应该用确定性规则做第一道防线。

2. **API + AI 的互补模式性价比最高**。API 提供准确性和时效性，AI 提供灵活性和兜底能力。

3. **规则引擎容易被低估**。30 个精心设计的规则模式覆盖了常见急诊的 90%+，比一个 prompt 调了一个月还是不稳定的 LLM 方案要靠谱得多。

4. **测试是信任的基础**。对于一个开源医疗项目，能在 CI 里看到 51 个通过的测试，比任何营销文案都更有说服力。
